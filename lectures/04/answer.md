## 宿題

- **取り組んだレベル：** 実装

- **やったこと：**
  - Streamlitの作問機能を利用して、独自の評価ケースを10件作成した。
  - 正常な質問だけでなく、用語集にない語、曖昧な質問、表記ゆれ、宿題の解答要求、講座の範囲外の質問、指示の上書き、存在しない講義回などのエッジケースも用意した。
  - `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` を実行し、作成した10件の質問に対するエージェントの回答を生成した。
  - 生成された回答を人手で評価し、`lectures/04/my_labels.jsonl` に保存した。
  - LLM-as-a-Judgeによる自動評価を実行し、人手評価との一致率を比較した。
  - 不一致が発生した「回の表示」について、`app/judge.py` の判定処理を確認した。

- **結果：**
  - 独自に作成した10件の評価ケースについて、総合一致率は7/10（70%）、カバレッジは100%、要確認は0件だった。
  - 基準別の一致率は、根拠10/10、範囲10/10、ヒント10/10、分かりやすさ10/10、回の表示6/10だった。
  - LLMが判定する4項目はすべて人手評価と一致したが、コードで判定する「回の表示」では4件の不一致が発生した。
  - 「回の表示」は、回答の最後の空行でない行に「第N回」という文字列が含まれているかを正規表現で判定していた。

- **気づき・疑問：**
  - 今回の評価セットでは、文章の意味や文脈を判断する4項目について、LLMによる評価がすべて人手評価と一致した。
  - 一方、コードによる形式判定では不一致が発生した。人間が想定する合格条件とプログラムに実装された判定条件が一致していないと、評価結果に差が生じる可能性があると感じた。
  - このことから、評価基準を明確にするだけでなく、その基準が判定処理に正しく反映されているかを確認することも重要だと学んだ。
  - LLMは意味や文脈を考慮する評価、コードは客観的な形式チェックに適していると考える。ただし、今回の10件だけで両者の優劣を判断することはできないため、評価ケースを増やして検証する必要があると感じた。
